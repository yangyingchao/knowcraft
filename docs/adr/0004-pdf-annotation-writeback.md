# ADR 0001：PDF 注释写回与写锁

- 状态：已接受
- 日期：2026-11-06
- 关联设计：`docs/superpowers/specs/2026-11-06-pdf-annotation-writeback-design.md`

## 背景

knowcraft 的 PDF 预览原本只读：页面渲染成图片，文本层用于选择。注释表已存在，
但没有写入口，也没有注释检索。用户需要高亮、下划线与便签，并希望在外部工具修改
PDF 后自动吸收。

## 决策

1. **PDF 为权威数据，数据库为缓存。** 注释写入 PDF 标准对象（`/Highlight`、
   `/Underline`、`/StrikeOut`、`/Text`），数据库只缓存用于列出、命中与索引。数据库
   丢失后通过扫描 PDF 重建。
2. **`/NM` 作为幂等键。** 由调用方预生成，同一 `nm` 重试不会产生重复注释。
3. **同步写回。** 创建或修改注释时立即写文件；文件被外部修改时拒绝写入并提供重扫。
4. **整文件原子替换。** 临时文件写入后 `fsync`、`rename`、目录 `fsync`，保留权限位；
   拒绝符号链接。
5. **core 增加写锁。** 进程内互斥加 `data_dir/.write.lock` 文件锁，所有写文件、
   数据库与索引的路径经它串行。锁顺序为写锁 → Store 连接锁 → tantivy 写锁。
6. **索引内容统一由 `Indexer` 组装。** `content` 为正文加全部便签文字；`selection`
   只是界面缓存，不进入索引。
7. **外部修改自动吸收。** watcher 检测 PDF 的写入完成事件，重新计算校验和，同步注释、
   标题与索引；校验和一致时直接返回，避免自写事件重复处理。
8. **边界。** 加密 PDF、签名 PDF、只读文件、符号链接与未登记文档不允许注释。docx
   注释不在本决策范围内。

## 后果

- core 从只读 PDF 提取扩展为可写 PDF，引入 `pdfcraft-annot`、`pdfcraft-cos` 与
  `pdfcraft-model`。`pdfcraft-render` 原本已在依赖图中，增量成本可控。
- 写回会改变文件校验和，去重、索引与预览缓存都需要同步更新。
- 大 PDF 的整文件重写有明显延迟，写回必须在后台线程执行。
- 外部进程在「校验后、rename 前」写入的窗口无法消除，只能拒绝或事后检测。
- 无 `/NM` 的第三方注释不会进入缓存；当前版本选择跳过，而不是猜测稳定键。

## 替代方案

- **数据库为主、PDF 为导出**：界面响应更快，但数据库损坏时可能丢失唯一副本，与用户
  的持久化目标冲突。
- **双写并定期比对**：冲突处理复杂，收益不足。
- **嵌入 pdfcraft 的 egui 界面**：需要 GTK 与 egui 的事件与渲染桥接，且 pdfcraft 的
  shell 假设自己拥有窗口，维护成本高。
